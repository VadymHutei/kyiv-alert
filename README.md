# Kyiv Alert

Невеликий сервіс на Python 3.14, який відстежує **лише місто Київ** через
[Neptun API](https://neptun.in.ua/api/v1/alerts). Повідомляє про появу та зняття
**червоного** рівня. Київська область і її райони не враховуються.

Зараз сповіщення виводяться в логи контейнера як `NOTIFICATION` із JSON-полями
`event_id` і `text`. Telegram відкладено: токен, chat ID та доступ до чату не потрібні.
У Python немає сторонніх залежностей; образ встановлює системну базу часових поясів
`tzdata`, щоб повідомлення показували київський час.

## Локальний запуск із тестовими даними

Потрібен запущений Docker Desktop із Linux containers і Docker Compose.
Команди виконуються з кореня репозиторію в PowerShell або терміналі Linux.

```sh
docker compose -f compose.yaml -f compose.mock.yaml up --build -d --wait
docker compose -f compose.yaml -f compose.mock.yaml logs -f alert
```

В іншому терміналі змінюйте стан mock API. Після кожної команди зачекайте приблизно
5 секунд, щоб сервіс встиг отримати новий стан:

```sh
docker compose -f compose.yaml -f compose.mock.yaml exec mock-api python tools/mock_api.py set red
docker compose -f compose.yaml -f compose.mock.yaml exec mock-api python tools/mock_api.py set yellow
docker compose -f compose.yaml -f compose.mock.yaml exec mock-api python tools/mock_api.py set off
```

Очікування: `red` створить одне повідомлення; повторний `red` — жодного нового;
`red → yellow` повідомить про зняття червоного зі згадкою, що жовтий залишається;
`yellow → off` буде без повідомлення. `red → off` також створює повідомлення про зняття
червоного рівня. Усі тестові повідомлення мають позначку **[ТЕСТ — симульовані дані]**.

Додаткові режими:

| Режим `set` | Що перевіряє |
|---|---|
| `oblast-red` | Червоний у Київській області без тривоги в місті — ігнорується |
| `invalid` | JSON без обов'язкового масиву — попередній стан зберігається |
| `error` | HTTP 503 — попередній стан зберігається |

Mock API доступний тільки всередині Compose-мережі, порти на ПК не відкриваються.
Після перезапуску самого mock API його стан повертається до `off`.

Перевірка збереження стану: встановіть `red`, дочекайтеся повідомлення та виконайте:

```sh
docker compose -f compose.yaml -f compose.mock.yaml restart alert
```

Повторного повідомлення бути не повинно. Після перерви понад 5 хвилин сервіс навмисно
надсилає актуальний стан із поясненням про затримку.

Зупинка зі збереженням тестового стану:

```sh
docker compose -f compose.yaml -f compose.mock.yaml down
```

## Запуск із реальним Neptun API

Спочатку зупиніть mock-стек наведеною вище командою. Потім:

```sh
docker compose up --build -d --wait
docker compose logs -f alert
docker compose ps
```

Цей режим теж надсилає повідомлення **тільки в логи**. На першому запуску без червоного
рівня повідомлень не буде. На першому запуску під час червоного буде повідомлення
«У Києві діє червоний рівень загрози».

Звичайний і mock-режими використовують **різні Docker volumes**, тому симульовані
стани не впливають на реальні. Обидва режими мають одне ім'я Compose-проєкту;
зупиняйте один перед переходом на інший і не запускайте кілька реплік `alert`.

Для перенесення на домашній сервер скопіюйте репозиторій і виконайте ті самі команди
звичайного запуску. Контейнер автоматично запускається після перезавантаження Docker
завдяки `restart: unless-stopped`. Вхідні порти та зовнішня БД не потрібні.

## Конфігурація

Необов'язково скопіюйте `.env.example` у `.env` та змініть значення.
Compose автоматично читає цей файл; секретів у ньому зараз немає.

| Змінна | Типове значення | Призначення |
|---|---|---|
| `ALERTS_URL` | `https://neptun.in.ua/api/v1/alerts` | Повний URL джерела |
| `POLL_INTERVAL_SECONDS` | `10` | Пауза після опитування; не менше 5 секунд |
| `HTTP_TIMEOUT_SECONDS` | `5` | Таймаут мережевої операції |
| `NOTIFICATION_MAX_AGE_SECONDS` | `300` | Поріг для повідомлення про поточний стан після перерви/затримки |
| `HEALTH_MAX_AGE_SECONDS` | `120` | Максимальний час від останнього успішного опитування для healthcheck |

У mock-режимі URL та інтервал навмисно перевизначені. Контейнер зберігає стан у
`/data/state.sqlite3`. При запуску без Docker шлях змінюється через `STATE_PATH`.
`DEMO_MODE=true` додає тестову позначку до повідомлень; у mock Compose він увімкнений.

## Стан, відновлення й діагностика

- SQLite зберігає останній рівень і чергу повідомлень. Оновлення стану та постановка
  повідомлення в чергу — одна транзакція. Доставлені записи зберігаються 7 днів.
- Успіх доставки зараз означає запис у stdout. Відомий стан не створює повторних
  повідомлень після звичайного перезапуску. Різні цикли тривоги мають різні `event_id`.
- Якщо доставка не вдалася, повторні спроби відбуваються зі зростаючою паузою до 5 хвилин.
  Опитування джерела продовжується. Після перезапуску незавершена доставка зберігається.
- Перед доставкою обов'язково отримується коректний поточний стан. Якщо стан змінився,
  старе невідправлене повідомлення замінюється актуальним. Це черга актуальних сповіщень,
  а не повний історичний журнал усіх переходів під час збою доставки.
- HTTP-помилка, таймаут чи неправильна структура JSON не означають зняття червоного.
  Відсутність Києва в коректному повному snapshot означає відсутність активного рівня.
- Невідомий/відсутній рівень у записі Києва вважається помилкою. Червоний має пріоритет,
  якщо в одній відповіді є кілька записів міста. `since` не використовується як час
  зняття тривоги; повідомлення явно містять час перевірки.
- `updatedAt` не використовується як heartbeat: незмінний стан може мати стару дату
  останньої зміни. Healthcheck спирається на час успішного отримання та перевірки відповіді.
- Healthcheck робить контейнер `unhealthy` після тривалої недоступності джерела.
  Docker автоматично перезапускає процес, що завершився, але сам статус `unhealthy`
  не спричиняє перезапуск. Сервіс продовжує пробувати отримати дані.
- Логи мають UTC-час, повідомлення всередині контейнера — `Europe/Kyiv` із переходами
  літнього/зимового часу. Ротація логів: 3 файли по 5 МБ для основного сервісу.

```sh
docker compose logs --tail 50 alert
docker compose exec alert python -m kyiv_alert --healthcheck
```

Звичайний `docker compose down` зберігає стан. **`down --volumes` видаляє стан відповідного
Compose-стека**, тому наступний запуск вважається першим.

## Тести

Unit-тести в контейнері:

```sh
docker compose build
docker compose run --rm --no-deps alert python -m unittest discover -v
```

Або локально з Python 3.14: `python -m unittest discover -v`.
На Windows без системної IANA-бази повідомлення при такому запуску показують час UTC.

Наскрізна перевірка реальних контейнерів із Python на локальному ПК:

```sh
python tools/smoke_test.py
```

Скрипт створює окремий Compose-проєкт із випадковим ім'ям і власним тестовим volume;
перевіряє появу червоного, відсутність дублів, перезапуск, помилки джерела,
перехід на жовтий, зняття червоного й ігнорування області. Після завершення видаляє
тільки контейнери, мережу та volumes цього тестового проєкту. Основний стек не зачіпає.

## Підключення Telegram пізніше

Додати реалізацію інтерфейсу `Notifier.send(event_id, text)` замість `ConsoleNotifier`.
Транспорт має підтверджувати успіх тільки після успішної відповіді Telegram,
перетворювати тимчасові помилки на помилку доставки та враховувати `retry_after`.
Токен і chat ID передаватимуться окремою конфігурацією, без зберігання в репозиторії
або логах. Поточні стани, тексти й черга не залежать від транспорту.

## Джерело та обмеження

Дані: [Карта повітряних тривог — NEPTUN](https://neptun.in.ua/).
[Документація](https://neptun.in.ua/developers),
[умови використання](https://neptun.in.ua/api-terms).
Інформаційний сервіс доповнює офіційні сповіщення. Орієнтуйтеся на офіційні сигнали
повітряної тривоги. Повідомлення про зняття **червоного рівня** не проголошує
відсутність усіх інших загроз.

Ключ міста `м. київ` підтверджений довідником `oblasts.geojson`. Парсер перевіряє обидва
масиви API й підтримує точні варіанти ключа `м. київ`, `м.київ`, `київ`, `місто київ`.
Під час початкової інтеграції активного запису Києва в API не було; позитивні сценарії
наразі перевірені синтетичними даними, тому реальний активний запис міста ще потрібно
зіставити з парсером, коли він з'явиться.

Polling snapshot не відновлює події, що почалися й завершилися між опитуваннями або
під час відсутності мережі/живлення. Також можливий повтор після аварії між записом
повідомлення транспортом і позначенням доставки в SQLite.
